# 0001. 参考プロジェクトからAI開発資産・ディレクトリ構成を移植する

## 背景

`vscode-gws-extension` は README.md に記載された「VS Code拡張 + Python API + Playwright/NotebookLM連携」
システムのうち、VS Code拡張部分のみを管理するリポジトリである。着手時点ではソースコードが存在せず、
issue駆動開発フロー・ドキュメントライフサイクル・Claude Code向けのagent/skill/hook等のAI開発資産も
何も整備されていなかった。

一方、作業者はリポジトリ直下（`.gitignore`済み・リポジトリ非同梱）の `参考ディレクトリ/` に、
無関係な別プロジェクト「nagame-ahk」（AutoHotkey v2製の常駐ツール）をローカルへcloneしていた。
このプロジェクトは製品としては本リポジトリと無関係だが、issue起票からマージまでを一貫して
Claude Codeで進めるための開発フロー（`issue-mr-flow` skill）・ディレクトリ構成規約・
GitHub/GitLab抽象化層・各種hook（セッション開始時のコンテキスト注入、push時の工数レポート）・
frontmatterベースのドキュメント索引（`index.jsonl`）システムなどが成熟しており、参考にする価値が
あった。

## 決定

**`参考ディレクトリ/` 配下のAI開発資産・ディレクトリ構成のうち、AutoHotkey固有の内容を除いた
汎用的な部分を、プロジェクト名等を汎用化した上で `vscode-gws-extension` へ輸入する。**

- `docs/spec`・`docs/ddr` はリポジトリ直下に置く（参考プロジェクトの設計を踏襲。`.claude/docs/`配下に
  作られていた空スキャフォールドは廃止した）。
- `dev-tools/src/vcs/{Provider,Github,Gitlab}.sh`、`archive-reentrant-plan.sh`、
  `extract-frontmatter.sh`、および対応する `dev-tools/docs/spec/*.md` はAHK非依存の汎用ロジックのため
  ほぼそのまま輸入した。本リポジトリのリモートはGitHubのみだが、`Gitlab.sh` も含め両対応のまま輸入した
  （移植コストがほぼゼロで、将来GitLabを使う可能性にも備えられるため）。
- `.claude/skills/issue-mr-flow/SKILL.md`（issue起票〜マージの23ステップの唯一のフロー定義）、
  `.claude/agents/issue-mr-resume.md`（セッション再開時の状態調査サブエージェント）、
  `.claude/hooks/{session-start,post-push-usage-report}.sh` と `lib/UsageTracking.sh`、
  `.claude/rules/{docs-workflow,git-workflow,plan-mode-safety,shell-script-style,powershell-encoding,markdown-frontmatter}.md`
  は内容が汎用的なため輸入し、プロジェクト名・issue番号等の固有参照のみ汎用化した。
  - `issue-mr-resume.md` は輸入元の時点で既に旧PowerShell版Provider（`Provider.ps1`、`Get-Issue`等の
    Verb-Noun関数）を前提にした記述のままで、実際の`dev-tools/src/vcs/Provider.sh`（bash・snake_case
    関数）への移行に追従できていなかった（参考プロジェクト側の記載漏れ）。輸入時にbash版の呼び出し
    （`source dev-tools/src/vcs/Provider.sh`、`get_issue`等）に修正した。
- `.claude/rules/directory-structure.md` は参考プロジェクトのAHKツリーに強く依存するため全面的に
  書き直し、既に決まっているメタ構成（`docs/`・`dev-tools/`・`.claude/hooks/lib/`・`plans/`・
  `worklog/`・`tests/`・`参考ディレクトリ/`の扱い）のみを記載した。拡張本体（`src/`）のレイアウトは
  未確定のため、TODOとして明示的に空けた。
- 「実装スキル」（参考プロジェクトの`ahk-implement`相当）・「コードレビューAgent」
  （`ahk-code-reviewer`相当）は中身がAHK固有でそのまま輸入できず、TypeScript/VS Code拡張向けの規約も
  まだ存在しないため、`.claude/skills/vscode-extension-implement/SKILL.md`・
  `.claude/agents/vscode-extension-code-reviewer.md` としてプレースホルダー（TODOスタブ）のみを用意し、
  中身の策定は見送った。
- `.claude/usage-state/feature-26-plan.json`・`feature-28-issue.json`（無関係プロジェクトのセッション
  由来の残骸ファイル）は削除した。参考プロジェクト自身の`.gitignore`も`/.claude/usage-state/`を
  除外しており、本来コミット対象ではないため、`.gitignore`に同様の除外を追加した。

## 却下した案

- **`docs/spec`・`docs/ddr`を`.claude/docs/`配下に置く案**: 着手時点で存在した空スキャフォールドの
  配置を踏襲する案。しかし参考プロジェクト自身の`.claude/docs/`も同様に空・退化した名残であり、
  正しい配置ではなかった。`.claude/`はエージェント設定（agents/skills/hooks/rules）に限定し、
  プロダクト・プロジェクトのドキュメントとは分離する方針を優先し、不採用とした。
- **実装スキル・コードレビューAgentの中身を今回策定する案**: ソースコードもコーディング規約も
  まだ存在しない段階でTypeScript/VS Code拡張向けの規約を新規に作ることは、実装が進む前に規約だけが
  先行し実態と乖離するリスクがあるため、プレースホルダーの用意に留め、規約策定は見送った。
- **GitHub限定でVCS抽象化層を簡略化する案**: 本リポジトリのリモートは現状GitHubのみだが、
  `Provider.sh`の分岐ロジック自体はプロバイダ非依存で移植コストがほぼゼロなため、`Gitlab.sh`を
  削って独自の簡略版を作るメリットが薄いと判断し、両対応のまま輸入する案を採用した。
